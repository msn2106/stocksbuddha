---
name: precommit-check
description: Check StocksBuddha changes before a Git commit for lint, formatting, unit tests, strictly greater than 90% coverage, JSDoc and README/docs accuracy. Use for pre-commit validation or commit-readiness reviews.
---

Run from the repository root. Read `git status --short` and preserve existing work.

**README and documentation accuracy is a required gate.** Read the code diff and search the root `README.md`, relevant `docs/` pages, workspace/database/script READMEs and other repository documentation for affected commands, paths, APIs, types, environment variables, configuration, setup steps, behavior and examples. Compare claims and code blocks to the current implementation, package scripts and tests. Follow renamed/removed symbols and check local links and file references. Inspect relevant documents even when they were not edited. Flag stale, invalid or incorrect code examples, obsolete commands and contradictory instructions with file/line references. Identify new behavior that needs documentation. If nothing needs updating, report which documents were reviewed and why they remain accurate. Check mode reports discrepancies without editing; use the fix skill to update them. Do not declare commit readiness until both the automated checks and this review pass. The shell command and Git hook cannot establish semantic documentation accuracy.

Run `npm run precommit:check`. This checks tracked changes against HEAD plus untracked files, without changing source or the index. It runs ESLint and Prettier on changed files, type checks, the complete unit suite (`npm run test:unit`) with fresh c8 coverage, and JSDoc validation. Integration and browser tests do not contribute to unit coverage. Generated coverage lives in ignored `coverage/precommit/`. Use `npm run verify` for lint, whole-repo unit coverage, security, integration, build and browser validation in the same order as CI.

Coverage must be **strictly greater than 90%**, independently for lines, statements, functions and branches in **each changed executable source file**, including tooling scripts. Exactly 90% fails. Whole-file checks intentionally include unchanged lines in a modified file. Missing coverage fails; tests, declarations and the explicit tool-configuration allowlist do not need their own coverage. Application configuration modules such as `src/config.ts` remain included. Type-only modules whose transpiled output has no executable code are omitted from runtime checks. Inline callbacks do not need separate JSDoc; named functions, function-valued variables/properties, classes, methods, constructors and accessors in changed source files need a meaningful JSDoc description. Review the descriptions for accuracy and add parameter/return/throw details where they clarify behavior; the syntax check cannot judge documentation quality.

For staged-only validation, use `npm run precommit:check -- --staged`. It refuses a working tree that differs from the index, including untracked code/config that could affect execution. Never stage, stash, reset or commit to make this check pass.

Report pass/fail for each category and actionable file/line diagnostics. A tool error, failed test, missing report or unmet threshold means the gate failed. Do not weaken rules, exclude changed code, add coverage-ignore comments, fabricate tests/JSDoc, or treat a global average as per-file coverage. When fixes are requested, use the sibling `precommit-fix` skill. This check alone does not authorize a commit.
