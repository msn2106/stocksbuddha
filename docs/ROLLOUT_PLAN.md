# Ordered rollout after the four review fixes

Prepared 9 November 2026. Keep `ONBOARDING_PRODUCTION_APPROVED=false` until the acceptance gates below are met. This plan covers the wider work; it does not claim those controls are already implemented.

1. **Deploy and verify this fix in isolated development.** Stop older app instances, back up the current DB/objects/keys, apply migrations through `1794441600000`, verify migration status, then deploy one matching release. Run the complete repository gate, disposable MariaDB tests and onboarding browser journey. Test revoked KYC, unpaid/future/expired subscriptions and historical receipts. Delay Drive requests while exercising unrelated tenant operations; test same-tenant busy responses, lease expiry, crashed workers and orphan reconciliation. Configure Sentry notification routing for background-stage errors and warning-level queue ages, then prove the notifications reach the responsible operator. Add independent worker/process liveness monitoring. Acceptance: recorded results, no client data exposed and an assigned recovery owner.

2. **Harden administrator access and uploads.** Enforce MFA for platform/RA administrators with enrollment, recovery codes, step-up for sensitive changes, session revocation and audited recovery; protect the storage account too. Add durable tenant/user upload byte/count/rate quotas with concurrent reservations, failed-upload accounting and administrator visibility. Establish a quarantine/malware workflow before parsing or inline previews. Load-test across multiple RAs and app instances with realistic file sizes and pool limits. Acceptance: bypass/recovery/quota/concurrency tests and documented operator procedures.

3. **Decide storage residency, retention and recovery before real KYC.** Confirm whether India-only storage is required; obtain a provider commitment covering primary objects, replicas, backups and subprocessors, or replace Gmail/Google One storage. Complete production OAuth verification/consent where applicable and test unattended refresh. Define retention and dispute/regulatory holds with the compliance owner. Establish independent DB/object/communication backups, separate encryption-key recovery custody, access reviews and restore objectives. Restore a complete synthetic tenant into an isolated environment and verify decryption, hashes, signed history, authorization and recovery time. Acceptance: approved storage choice, retention schedule and a witnessed restore record. Private Drive folders alone satisfy none of those acceptance gates.

4. **Finalize the RA's KYC and signing procedure.** Have the RA/compliance adviser approve supported client categories, KRA/AML checks, required declarations, evidence, correction/rejection/review duties and retention of prospect/client communications. Approve complete MITC/terms and the signing mode; integrate a suitable signing provider if required, authenticating callbacks and retaining independently verifiable evidence. Current typed-name/email-code consent is not CCA eSign. Acceptance: approved procedure and wording, signed-provider validation where applicable, and negative tests for stale/forged/cross-tenant evidence. See [CCA's eSign description](https://cca.gov.in/eSign.html).

5. **Complete paid cancellation, refunds and billing.** Agree cancellation policy and effective service-end calculation with the RA; implement proportional entitlement changes, idempotent gateway refunds, partial/failed refund recovery and immutable audit history. Have a tax adviser specify applicable GST treatment, registration, place of supply, component splits, numbering and credit notes. Implement those reviewed fields and embed licensed Unicode fonts for multilingual PDFs. Acceptance: sandbox cancellation/refund/reconciliation tests, tax examples approved by the adviser and visual PDF QA in each supported language.

6. **Prove real integrations in the isolated environment.** Use separate development DB, storage, OAuth, mailbox, merchant and Sentry environments with synthetic records. Verify real Drive upload/download and revoked-token recovery; mailbox attachment equality and bounce handling; Cashfree order creation, authenticated webhook replay, provider-confirmed status, missed-webhook reconciliation and refund flows. Sandbox tests do not prove live settlement; validate a controlled live transaction/refund only under an approved merchant test procedure. Acceptance: evidence from each provider and tested runbooks for outages and delayed callbacks.

7. **Run a controlled production pilot.** Complete the unresolved [production review](SEBI_RA_REVIEW.md), appoint operational owners and on-call recipients, approve retention/communications and refund procedures, and deploy with production secrets and verified TLS. Confirm source maps, alerts, backups and migration status on that exact release. Enable production only after the review is signed off, initially for one RA and a small approved cohort. Monitor settlement, delivery age, eligibility denials, storage/quota usage and recovery outcomes; define stop criteria and a forward-recovery plan. Expand only after a documented pilot review.

The communications procedure must cover relevant interactions from first contact, including prospective clients, with applicable holds. The [23 October 2026 SEBI circular](https://www.sebi.gov.in/sebi_data/attachdocs/oct-2026/1792753022042.pdf) is a source for compliance review; obtain approval for the actual operational procedure rather than treating software logs as the complete record.
