# Internationalization

Only **English (`en`) and Hindi (`hi`)** are enabled for launch. Kannada, Gujarati and Marathi are not registered, advertised or populated with placeholder translations.

## Catalogue structure

`frontend/src/locales/en.json` and `hi.json` are parallel flat JSON objects. Identifiers describe the meaning/location of a message and remain stable when wording changes:

```json
{
  "nav.subscribe": "Subscribe",
  "preferences.textSize": "Text size",
  "about.belief": "{name} is built around a simple belief: understanding the reasoning matters as much as knowing the view."
}
```

```json
{
  "nav.subscribe": "सदस्यता लें",
  "preferences.textSize": "अक्षर आकार",
  "about.belief": "{name} का आधार एक सरल विश्वास है: राय जानने जितना ही उसके तर्क को समझना महत्वपूर्ण है।"
}
```

Components reference identifiers, never English sentences or a previously translated value:

```tsx
const { t } = useLanguage();
<button>{t("nav.subscribe")}</button>;
<p>{t("about.belief", { name: tenant.profile.name })}</p>;
```

Change copy in the relevant JSON file; do not rename the key unless the message's meaning changes. Use a complete interpolated sentence when dynamic values need to appear in different positions in different languages. Values render as React text, not HTML. Financial/legal translations still require RA approval before publication.

`frontend/src/locales/messages.ts` owns the catalogue registry, `MessageKey` type, translator and language options. The English JSON defines the compile-time key union; every enabled catalogue must contain matching keys. Unknown keys are TypeScript errors and also fail explicitly at runtime. Missing interpolation values fail explicitly. An unexpectedly missing target-language value falls back to English, not to a raw identifier; the parity tests should catch such omissions before release.

Built-in demo-tenant copy uses explicit `tenants.*` keys selected by the seed registry in `messages.ts`. Those catalogues own the rendered built-in copy. Arbitrary tenant-authored text is separate content and is never passed to `t()` as a key. When the tenant editor is implemented, its content will need approved per-language published revisions; do not use sentence lookup or silently infer translations from user text.

## Adding another language later

1. Add its code to `supportedLocales` in `packages/contracts/src/locales.ts`. The `Locale` type and backend URL/cookie validation derive from this list.
2. Add a fully translated JSON catalogue with the same identifiers and interpolation placeholders as English. Register it in `catalogues` in `messages.ts`; type checks flag missing registry entries or messages.
3. Add its `languages.*` native-name key to every catalogue and map its code to that key in the language-option registry. Native labels must use their own language/script consistently in every catalogue. The switcher renders registered options automatically; components and server routing do not need language-specific conditionals.
4. Configure suitable fonts/script styling, review translation quality and legal wording, and extend the language/browser acceptance coverage. Explicitly update the launch-language assertion when the new language is approved.
5. Run `npm run verify` before publishing.

This small catalogue engine currently supports plain messages and named interpolation. Pluralization/date/number/currency formatting should be introduced deliberately when product content needs it; do not build these by joining translated fragments. The catalogue file format and semantic identifiers can be retained if a dedicated i18n library becomes useful later.

## Verification

`frontend/tests/i18n.test.ts` runs through `npm test` and checks key parity, nonempty values, semantic key shape, placeholder parity, independent English-copy changes, interpolation order/literal values, rejection of sentence/unknown keys, launch languages and the separation of tenant-authored content from translation identifiers. Frontend tests are included in the frontend TypeScript check.

The existing Playwright suite checks server-rendered English/Hindi, language switching, cookie persistence, same-tenant navigation, translated dialogs/disclosures, no-JavaScript navigation and accessibility behavior. Run `npm run build && npm run test:e2e` for browser acceptance.

Verification after the refactor: `npm run verify` passed, including 7 frontend i18n tests, 4 backend tests, 2 dependency-policy tests, all 10 Playwright scenarios, workspace type checks, production builds and formatting. The full workspace audit reported zero known vulnerabilities. No new dependencies or launch languages were added.
