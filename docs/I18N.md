# Languages and tenant-owned content

Only English (`en`) and Hindi (`hi`) are supported today. Language support has three independent content sources:

- `frontend/src/locales/en.json` and `hi.json`: application-owned UI, navigation, accessibility controls and current shared disclosure/pending states.
- `frontend/src/platform/content.ts`: application-owned platform brand copy in English/Hindi, including homepage metadata and audience-specific sign-in guidance. It never inherits tenant content.
- `backend/src/websites/seeds/<tenant>/<locale>.json`: tenant-owned website content for the seed adapter. MariaDB mode stores all enabled-language content inside a tenant-owned website revision snapshot; public projection still returns only the selected locale.

Shared UI and tenant website catalogues use stable semantic keys and string values. Platform copy uses a typed locale map with strings and feature-list entries. Shared UI uses `nav.subscribe` or `preferences.textSize`; website content uses `site.hero`, `about.belief` or `faq.audience.answer`. `packages/contracts/src/content.ts` defines the supported website fields. There are no tenant-slug branches or `tenants.alpha.*` keys in the browser translator.

```tsx
const { t } = useLanguage();
<button>{t("nav.subscribe")}</button>;
<p>{t("about.belief", { name: tenant.profile.name })}</p>;
```

The request resolver selects an enabled tenant language before SSR and sends only that language's website content to the browser. Unsupported/disabled language requests fall back to the tenant's default language for the whole page. Every enabled language needs complete, nonempty content with matching interpolation placeholders before a revision can validate. No tenant's missing translations fall back to another tenant or a shared marketing catalogue.

`messages.ts` combines shared UI with the supplied website content for that render. Authentication/accessibility controls remain application-owned; approved optional public copy keys can be overridden by tenant content. Unknown/missing keys and missing interpolation values fail explicitly. Values render as text, not raw HTML. A value such as `nav.subscribe` remains literal text when entered into a tenant headline. Named interpolation supports translated word order; plural/date/number formatting is not implemented yet.

Language options are filtered by the resolved website's enabled languages. Preferences use a tenant-specific cookie name and path; changing Alpha's language does not change Beta's language. Cookies have no parent-domain attribute, so development and production hosts remain separate. Accessibility display preferences intentionally remain device-wide.

The platform homepage uses the explicit `?lang=en` or `?lang=hi` query, defaults to English, and shares the display controls. It writes no tenant language cookie; choosing a platform language does not change an RA’s saved preference. See [platform website](PLATFORM_WEBSITE.md).

## Editing and adding languages

For current seed previews, edit the relevant tenant's English/Hindi JSON files; other tenants are independent copies. Validate financial/legal wording with the RA before publication. In MariaDB mode, RA owners edit customer content through the authenticated [website editor](WEBSITE_EDITOR.md), with draft/preview/publish operations instead of source-file writes.

To add a platform language:

1. Add its code in `packages/contracts/src/locales.ts` and its content slot in `websiteRevisionSchema`.
2. Add its complete shared UI JSON, register it in `messages.ts`, and add its native language label to all shared catalogues.
3. Add complete platform homepage copy in `frontend/src/platform/content.ts`, including title, description, access instructions and demo enquiry text.
4. Add translated content to each tenant that enables it; update that tenant's enabled/default language settings deliberately. Other tenants need not enable the new language.
5. Review script fonts, translations, placeholder parity, fallback behavior, SSR metadata and accessibility, then extend tests and run `npm run verify`.

Frontend tests verify UI catalogue parity, literal interpolation, per-render content isolation and shared-control protection. Backend tests verify tenant language defaults, complete publication content and placeholder parity. Playwright verifies SSR, same-tenant language persistence, independent tenants/tabs, no-JavaScript navigation and English/Hindi accessibility. See [architecture and current limits](ARCHITECTURE.md).

The owner website editor supports bilingual draft content and optional public copy overrides (`optionalWebsiteContentKeys`). Existing immutable snapshots may omit these optional keys; shared public copy is then the fallback. Authentication and accessibility controls cannot be overridden. Required tenant content never falls back to another website. Enabled languages need complete required content before preview/publication. Only the two analyst introduction fields support the `{name}` placeholder; other fields reject interpolation placeholders to prevent rendering failures.
