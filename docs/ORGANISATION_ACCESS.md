# Platform owner, RA Admin and team access

The login identity is global. **One email has one current role within each RA; Subscriber and staff roles are mutually exclusive.** See [role exclusivity](ROLE_EXCLUSIVITY.md) for the complete matrix, messages, privacy and concurrency rules. The selected login section determines the intended destination, while current database roles determine access. Selecting Organisation never grants a role or enrolls the user as an investor.

The public platform website is `/`; its access section routes RA members explicitly to their organisation login. `/login` and `/signin` no longer choose the StocksBuddha RA implicitly. Demo enquiries do not create accounts or organisations. See [platform website](PLATFORM_WEBSITE.md).

## Routes and roles

| Route                        | Access / purpose                                                                                          |
| ---------------------------- | --------------------------------------------------------------------------------------------------------- |
| `/workspace/login`           | Platform-owner sign-in; no public platform-owner signup                                                   |
| `/workspace/verify-email`    | Verify the shared platform identity, returning to platform login; no RA context or role grant             |
| `/workspace/forgot-password` | Send platform password recovery email                                                                     |
| `/workspace/reset-password`  | Reset the shared password using a platform-path HttpOnly token cookie                                     |
| `/workspace`                 | Verified platform owner only; blank workspace shell                                                       |
| `/workspace/organisations`   | Create a draft organisation and invite its first RA Admin, or invite an admin to an existing organisation |
| `/ra/:slug/login`            | Same URL with Investor / Organisation radio capsule                                                       |
| `/ra/:slug/account`          | Subscriber account shell, requiring an active Subscriber membership                                       |
| `/ra/:slug/workspace`        | Organisation shell, requiring active `owner`, `analyst` or `support` membership                           |
| `/ra/:slug/workspace/team`   | RA Admin invitations, resend/cancel actions and tenant access revocation                                  |
| `/ra/:slug/invitation`       | Set up or sign in with the invited identity and join using a valid invitation                             |
| `/workspaces`                | Authenticated cross-RA chooser; links investors to account and staff to workspace                         |

The database tenant role `owner` is labelled **RA Admin** in the organisation UI. It is distinct from `auth_users.platform_role='owner'`, labelled **Platform owner**. Existing analyst/support/subscriber roles retain their meaning. Platform ownership does not implicitly create tenant membership. Only platform owners can appoint RA Admins or change their roles, including through the existing membership PATCH API. On the Team page, an active RA Admin can revoke another member’s access, including another RA Admin’s access; self-revocation is denied so the acting administrator remains active. An RA Admin can invite analysts/support solely to their own active organisation; other team members cannot invite or promote users.

On the tenant login form, Investor leads to the investor account or verified subscriber enrollment. Organisation leads only to a staff workspace; an account without a staff role gets an access message and the newly created login session is revoked. Existing staff are rejected from Investor login, the subscriber dashboard and enrolment with a message to sign in under Organisation. Subscribers are rejected from staff invitations and Organisation access; the RA Admin must use a different email. The platform login independently checks the current stored platform role and verification state.

The authenticated overview intentionally has a blank main area, brand logo/name, left navigation and a top-right Profile control. The profile shows name, email, verification, current role and organisation. Research and settings navigation entries are disabled and marked Coming soon. Documents is functional for platform owners, RA members and customers, with uploads requiring backend Google OAuth configuration; see [private document storage](GOOGLE_DRIVE.md). Organisations and Team are functional management pages for the appropriate roles. RA Admins also see **Edit website** at `/ra/<slug>/workspace/website`; platform ownership alone and investor/staff access do not grant editor permissions. See the [website editor](WEBSITE_EDITOR.md). The sidebar collapses on narrow screens; the profile uses the existing Radix dialog primitive with focus restoration and Escape handling. Shared English/Hindi labels and existing fonts/colours are reused.

## First platform owner: explicit operator bootstrap

Use an existing global account for the first owner. There is no public owner signup: creating a tenant investor account is not a required owner-onboarding step. For an existing unverified identity, open `/workspace/verify-email`, submit its email, and follow the configured Hostinger SMTP link back to `/workspace/login`. Verification does not assign any role or tenant membership. Then, from an authorised operator checkout with the intended database credentials:

```sh
npm run db:migrate -- --target dev
npm run auth:bootstrap-owner -- --email your-verified-email@example.com --target dev
npm run dev
```

The CLI requires `DB_ENV` to match the explicit `--target`. It only assigns an existing verified identity, refuses replacing another platform owner, is repeatable for the same owner, and writes a platform audit event. It never creates a password or marks an email verified. No public bootstrap or platform-role assignment endpoint is exposed. No local real account is promoted automatically by migrations or application startup. The operator command runs from the source checkout; it is not part of the standalone migration CLI artifact.

Open `/workspace/login` and use the existing email/password after bootstrap. The login links to `/workspace/verify-email` and `/workspace/forgot-password`; recovery stays under `/workspace` and never redirects to an RA join page. Successful password reset returns the platform sign-in form and does not grant access. Platform and tenant reset cookies have separate names and paths; raw reset tokens are removed from the URL before rendering. These public recovery pages deliberately work before platform-role assignment, but the protected workspace still checks the verified, current stored owner role. Restart the development process after changing `SMTP_USER`, `SMTP_PASSWORD` or `AUTH_EMAIL_FROM` in `backend/.env`, because the email adapter is configured at startup.

Open `/workspace` to sign in. Local fixture mode cannot authenticate owners or send invitations. Administrator MFA is still a separate production-readiness requirement; this change does not implement MFA.

## Organisation setup and invitations

The platform owner enters the organisation name, legal name, unique slug, brand initials, RA Admin full name and email. The organisation is created as `draft`, with no public website or fabricated research content. An invitation is issued for the intended email and the server-stored role `owner`. Once the recipient completes invitation signup or authenticated Organisation sign-in, the matching staff membership is created or confirmed and the organisation becomes active in the same transaction. Website publication is an explicit action in the RA owner editor; activation alone does not create a public page. Existing demo organisations can receive explicit admin invitations without recreating their identities.

Invitations do not pre-create passwords or duplicate an existing global identity. A new recipient opens the invitation and sees their stored name and locked email prefilled. They choose a password and select **Create account and join**. The valid email-bound invitation is the email proof: no second verification email or acceptance step is required. In one transaction the server validates the current issuer and unused/unexpired grant, creates a verified global account and hashed credential, creates membership and consumes the invitation. Better Auth then authenticates that account using the chosen password and issues the normal session cookie. If session creation is interrupted, the account/membership remain valid and the user can sign in normally with that password. Existing accounts are never overwritten or silently verified; verified existing users with no membership in this RA, or with the exact invited staff role, sign in with their existing password through **Organisation**, which consumes a compatible invitation and opens the workspace. Existing subscribers and different staff roles are rejected with the different-email guidance. A matching already-signed-in account completes acceptance through an automatic same-origin POST, with a Continue fallback for browsers without JavaScript. GET inspection never consumes a grant. If an invitation is opened while signed in with another identity, the page explains the mismatch and offers **Switch account**, which signs out the shared session while retaining the invitation cookie. Signed-in users can instead choose **Back to my workspaces** to keep their existing login and resume their own work. This return link also appears on unavailable/expired invitation screens. An existing matching unverified account is prompted to verify its email before acceptance; verification resends preserve the invitation callback instead of sending the recipient to subscriber enrollment. The invitation remains in a tenant-path HttpOnly, SameSite=Lax cookie while setup/login completes. The raw credential is removed from the URL on first inspection and never put into hydration data or the invitation listing. Cookies are Secure on HTTPS and contain no role grant; the server rechecks the stored invitation on acceptance.

Migration `CreateOrganisationInvitations1793491200011` adds `organisation_invitations`. It stores a SHA-256 token digest, tenant, normalized email, role, issuer, one-hour expiry, delivery state and acceptance/revocation state. Forward migration `AddInvitationNames1793491200012` adds the recipient full name, required for all new invitations and used in the email greeting. Historical invitation names remain NULL; enter a name when resending an older invitation. Raw tokens are sent only to the recipient through the existing bounded Hostinger SMTP adapter. Issuing another invitation for the same tenant/email revokes older pending invitations. Delivery failures retain safe state; sending again creates a new credential rather than recovering a stored bearer token. No provider response or secret is included in errors.

Existing-account acceptance requires a current session and verified matching email; invitation signup requires no existing account for the stored email. Both require the exact tenant, unexpired unused/unrevoked invitation and an issuer whose current permissions still authorize the grant. The transaction locks affected users in sorted order, then tenant and invitation/membership records, rejecting every incompatible existing role and denying revoked memberships. Concurrent acceptance creates one membership and consumes the grant once. Invite-only signup is limited to 10 attempts per trusted client IP per minute in shared MariaDB storage before hashing; it uses the pinned Better Auth password hash format. Ordinary public signup still requires the usual verification email. The Subscriber/Investor login capsule ignores outstanding invitations and opens the dashboard only for subscribers (or enrolment when no role exists); staff receive a role-specific denial; selecting Organisation never grants a role without the stored invitation or staff membership. Client-supplied email, role, tenant and verification flags cannot alter the invitation grant.

An invitation cannot reactivate revoked membership, grant platform ownership, convert a subscriber to staff, change one existing staff role to another, or grant access to a different tenant. Issuance and resend reject such conflicts before replacing links or sending email; acceptance rechecks legacy and concurrent conflicts. Creation, invitation issuance and acceptance write audit events atomically with their respective database mutations. Email delivery occurs after commit and is not an atomic part of that transaction.

The RA Admin Team page requires full name, email and role for new team invitations. Each unaccepted, unrevoked analyst/support invitation has **Resend invitation** and **Revoke invitation** icon actions (with hover/focus tooltips and accessible names), including after expiry or failed delivery. Resending retains the stored recipient, full name and role, creates a new one-hour credential and revokes older pending credentials. Admin appointment invitations remain a platform-owner operation. Resending does not restore revoked membership.

The same page lists all organisation members, including users with no invitation history. **Revoke access** asks for confirmation, revokes only the selected user's membership in this organisation, and cancels their pending invitations. Their global login and memberships in other organisations remain intact. These new resend/revoke actions require a verified, active tenant `owner` with no capability overrides, freshly checked within the mutation transaction; analyst, support, subscriber and platform ownership alone cannot use them. Every action checks the request Origin and records an audit event. Revocation works even when SMTP is unavailable. The existing membership PATCH API retains its reviewed staff-to-staff role-change policy, but subscriber/staff conversion is forbidden.

Invitation credentials are consumed by the successful setup/sign-in transaction or the same-origin acceptance POST for an already-signed-in recipient. Inspecting a link with GET never consumes it. Ordinary account-verification credentials keep their separate single-use lifecycle.

Organisation creation and admin-email delivery are separate operations: a delivery failure can leave a draft organisation. Refresh Organisations, select that existing organisation and send its admin invitation again. Duplicate slugs are rejected; no hidden destructive cleanup occurs.

## Verification

TDD began with failing policy, service, bootstrap and React shell tests. Unit tests exercise role/destination separation, tenant-scoped invitation permissions, hashing, delivery state, verified recipient binding, single-use/expiry denial, staff-role preservation and operator bootstrap. MariaDB integration tests use disposable databases to verify actual constraints, draft activation, cross-tenant denial, concurrent acceptance and issuer/membership revocation.

```sh
npm run test:unit
npm run test:coverage
RUN_DATABASE_TESTS=true npm run test:database
npm run build
npm run test:e2e
npm run test:e2e:organisations
```

The organisation Playwright suite needs local dev administrative database credentials (`DB_ROOT_PASSWORD` in ignored `backend/.env`) to create and remove only disposable `sb_test_*` databases. It captures verification/invitation emails in memory and never sends real messages. Its test-only server creates verified fixture accounts and a fixture platform owner; those grants do not touch the configured application database. It checks real owner/admin/team navigation, profile dialogs, role denials, responsive screenshots, hydration and axe accessibility. The fixture disables Better Auth credential rate limits to avoid shared test traffic buckets; dedicated auth integration tests continue to verify the production limiter.
